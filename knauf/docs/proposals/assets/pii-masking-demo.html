PII Protection Strategy · Agentic Karl KK20-207 · discovery deliverable · demo

The short version

Protect the durable copies and the logs first. Don't mask prompts before the model — the in-tenancy model call is the least risky hop; the real GDPR exposure is data that persists without a purpose.

Agentic Karl handles personal data everywhere a chat assistant does. LibreChat provides none of the protection out of the box, so Knauf builds or buys it. This demo summarizes the assessment; the full proposal has the citations, the risk register, and paste-ready follow-up tickets.

LibreChat, out of the box
No PII masking
Secrets-only log redaction, content moderation, and temporary-chat retention exist. PII masking is an unmerged, opt-in-only upstream request.
Where the risk actually is
Logs & retention
Debug logs capture chat content (on by default); conversations, memories & the search replica have no TTL; shared links are public by default.
The engine choice
Left open · PoC decides
Presidio, Azure AI Language, a hybrid, or a commercial tool. A proof-of-concept on Knauf data settles it — not vendor claims.
The plan
5 phases · Ph0 is config
Phase 0 is config-only quick wins (started in this PR). Masking engines don't appear until Phase 3, at persistence chokepoints.

Why not just mask everything before the model?

A corporate assistant is supposed to reason over names, customers, and projects — "draft an email to Frau Müller about the Iphofen order" only works if the model sees "Frau Müller". Azure OpenAI already runs inside Knauf's tenancy under no-training terms and the EU Data Boundary, so the model call is a controlled hop, not a leak. Masking it by default would wreck utility and push people to public ChatGPT — a worse privacy outcome, and exactly the line upstream drew ("strictly opt-in only"). So masking is reserved, opt-in, for designated high-risk flows; the effort goes where data lingers.

Engine options — no pick made here

Four viable engines. The decision belongs to legal + security + architecture, made on Knauf data.

Option A · Tier 3

Presidio, self-hosted

  • Free / open source; runs on AKS
  • German model + national-ID recognizers
  • EU-resident by construction
  • NER accuracy below managed; verify governance
Option B · Managed

Azure AI Language PII

  • Managed accuracy, ~77 languages
  • Container option = data stays in-tenancy
  • Per-record cost at chat volume
  • German conversational PII is preview-only
Option C · Hybrid

Presidio + Azure recognizer

  • Presidio orchestrates; Azure for hard entities
  • One surface, managed accuracy where it counts
  • Choosing A keeps this open
Option D · Commercial

Private AI / Skyflow

  • Best language coverage; reversible tokenization
  • Self-host container / residency regions
  • Licensing cost — fallback if PoC fails

Decision criteria: German + multilingual accuracy on Knauf sample data · EU residency · cost at real volume · operational burden · fit to the tier ladder. The mechanism is a PoC spike — stand up the candidates, measure on labeled Knauf data, decide.

Phased roadmap

Ph 0Tier 0

Config quick wins

Default DEBUG_LOGGING off (started here), document logging posture, review shared-link default, fix OpenID info-level PII log. Days of effort, biggest exposure cut.

Ph 1Tier 5

Log-layer PII redaction

Extend the secrets-only redactor with email / IP / phone / IBAN / ID patterns at all log levels. Upstream-contribution candidate.

Ph 2Tier 0/5

Retention & minimization

Real TTLs for conversations, memories, shared links, violation records; verify delete propagation to search + storage. Needs a DPO retention decision.

Ph 3Tier 3

Engine PoC + persistence masking

Run the PoC → decide the engine. Then mask at two non-streamed chokepoints: shared-agent knowledge ingestion and memory writes.

Ph 4gated

Opt-in inline masking

For designated high-risk flows only, input-side (streaming-safe), with re-hydration. Requires an explicit product decision.
