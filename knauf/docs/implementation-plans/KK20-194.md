## Context

Users paste URLs to Karl expecting him to open and summarise them. Today Karl
either refuses or responds "could not extract page contents". Root cause: the
Azure OpenAI Responses API ignores the `web_search` tool that LibreChat
forwards, and no scraper/search provider is wired in. We want to fix this
without onboarding any third-party SaaS data processor, to preserve GDPR /
data-residency posture and keep compute inside the Azure tenant.

Full design and option matrix: see
[docs/kk20-194-open-url-tool-proposal.md](../../../docs/kk20-194-open-url-tool-proposal.md).

## Approach

Implement a lean, in-tenant `open_url` tool (per the proposal doc) instead of
adopting Firecrawl cloud / Serper / Tavily / Jina cloud / Bing grounding.
Detailed approach to be finalised during proposal review on this draft PR;
update this section once the option is locked.

Suggested next steps once the approach is approved:

- Add the `open_url` tool registration on the API side (LibreChat tool plugin).
- Wire it into the default chat + agent builder allow-list (`librechat.yaml`).
- Add a Knauf seam if any upstream files are touched (see
  `fork-management` skill).

## Acceptance Criteria

From KK20-194:

- Karl can open a user-pasted URL and use its contents in his reply.
- No third-party SaaS data processor is introduced; traffic stays within the
  existing Azure tenant.
- Works for both the default chat endpoint and agent builder agents.

## Spec Impact

- `librechat.yaml` (agent capabilities / tool allow-list) — likely.
- `packages/api/src/endpoints/openai/llm.ts` (tool translation) — possibly,
  to stop forwarding the no-op `web_search` once `open_url` replaces it.
- New Knauf-owned tool module under `packages/` or `api/` — to be decided.
- `SEAMS.md` — required if any upstream file gets a `[knauf]` seam or a new
  `knauf/` file is added (run the `seam-manifest` skill).
